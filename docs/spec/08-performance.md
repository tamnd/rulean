# 08. Performance

This document turns promise P1 (02.2) into budgets, names the techniques that pay for them, and specifies how performance is measured and protected in CI.

Evidence: research/B-kernels-and-performance.md sections 8 to 10, and research/A section 5.

## 08.1 The budget

The P1.a target is at most 1.21 T instructions on the Arena Mathlib export, including parsing. Mathlib has about 700 k declarations.

| Phase | Budget, instructions | Per declaration | Official today | Best known (unverified) |
|---|---|---|---|---|
| read and parse (07) | 0.16 T (NDJSON) or 0.03 T (`.rlb`) | 230 or 45 | 1.66 T (14%) | nano-lean whole pipeline about 68 per byte |
| scheduling, environment cuts, merge | 0.02 T | 30 | none | |
| engine F: infer, whnf, conversion | 0.85 T | 1.2 M | about 10 T | nano-lean about 0.5 M, gruszka about 0.53 M |
| engine R rescues and confirmations (05.1) | 0.08 T | 0.1 M | | |
| inductives, recursor generation, quotients | 0.05 T | | | |
| report, axiom closure | 0.02 T | | | |
| **total** | **at most 1.18 T** (margin 0.03 T) | **at most 1.7 M** | 12.10 T (v4.35.0) | 0.40 T |

The stretch goal is 0.60 T. That is 20 times fewer than v4.35.0 and 16 times fewer than the 2026-11-14 nightly. It is the planned answer to the official kernel getting faster (15.2).

Every budget row has a counter in the bench harness (08.7). A pull request that makes a row exceed its budget on the Init or Std corpus fails CI.

## 08.2 Where the factor comes from

The factors are ranked by evidence (B§10.2). They multiply only roughly, so the plan has margin.

| Rank | Technique | Expected factor vs official | Evidence | Spec |
|---|---|---|---|---|
| 1 | NbE with glued values and lazy delta by value | 3 to 6 | the top three Arena kernels all use NbE, 0.40 to 0.53 T, against 2.6 to 5.8 T for substitution kernels in Rust; 100 to 1000 times on the `perf/` tests | 05.4 |
| 2 | handle store, struct of arrays, no reference counting | about 2.3 | con-ron against con-leche, same algorithm, 3.85 T against 8.85 T; allocation and RC are 25% of the official profile | 04 |
| 3 | fast input | about 1.15 (removes most of the 14%) | official parse-only 1.66 T; MM0; gruszka Susz | 07 |
| 4 | session caches across declarations | 1.2 to 2 (to be measured) | gruszka sessions, measured only in its design doc | 08.4 |
| 5 | build tuning: fat LTO, one codegen unit, PGO | 1.1 to 1.2 | con-ron −11.6% on Init with LTO | 13.3 |
| n/a | threads | none on instructions | 3 to 9 times wall time at 4 to 8 threads, +3.5% instructions | 08.3 |

con-ron is at 3.47 T. Techniques 1, 3 and 4 must give a further factor of 2.9 over con-ron to reach 1.21 T (B§10.1). Technique 1 alone gives about 5 to 14 times among unverified Rust kernels. So the plan needs about half of what NbE gave those kernels.

## 08.3 Parallel scheduling

Parallelism does not help P1 (instructions). It is needed for P1.e (60 s wall on 8 threads).

### 08.3.1 Dependency graph

- After parsing, the scheduler computes the direct constant references of each declaration (type and value). This is one pass over the frozen store with a per-node "constants below" summary, cached per node.
- A declaration can be checked when all its references have been **added** to the environment. Added means the constant is known with its type, not that its check has finished. This is how the official kernel works in parallel elaboration: later declarations use the type of a theorem before its proof is checked.
- So the scheduler has two stages per declaration: **add** (register the constant, cheap, in declaration order) and **check** (the expensive part, in parallel). Inductive declarations are added only after they are checked, because their recursors are generated by the check.
- A later declaration may be checked before an earlier one it uses has finished its check. If the earlier check fails, the run verdict is `reject`, and the report marks the later declarations as `depends-on-rejected`. Theorem T1 applies only to a run whose verdict is `accept`, so this order is sound.

### 08.3.2 Environment cut

- Each check job sees the environment of all constants added before it, in input order. That is the environment that the official kernel would see when replaying the export in order.
- The environment is an append-only array of constants indexed by declaration number. A cut is a number: "constants with index below k". So a cut costs nothing to make or share.
- A worker that looks up a constant with index at or above its cut gets "unknown constant", exactly as the sequential replay would.

### 08.3.3 Jobs and granularity

- Mathlib parallelises almost completely: the slowest single declaration takes about 0.7 s (con-leche) and the slowest FLT declaration about 3.7 s (gruszka) (B§8.4).
- Jobs are groups of consecutive declarations from the same module, up to about 2 M instructions of estimated work, so the per-job overhead stays below 1%.
- Declarations with a large estimated cost are scheduled first (longest-processing-time first within the ready set). The estimate is the size of the value in nodes.
- con-leche reaches 8.8 times at 8 jobs, gruszka 5.2 times (B§8.4). The rulean target is at least 6 times at 8 threads on Mathlib.

### 08.3.4 Determinism

The verdict and the report do not depend on the thread count (T5, 10.1). Workers do not share caches. A session cache entry that one worker makes is not visible to another worker, so a worker's results depend only on its own job sequence. Each job's sequence is a function of the scheduler's deterministic job list, not of timing.

**Why not share caches between workers.** Sharing would save some work. It would also make the cache contents depend on timing. A cache entry is a true judgment, so sharing would still be sound, but it would make performance timing-dependent and the proof harder. rulean 1.0 does not share. A later release may add a read-only cache layer that is built in a first pass and then frozen.

## 08.4 Sessions: caches across declarations

The official kernel clears its caches after each declaration. rulean keeps some of them in a per-worker **session** (B§8.3, gruszka).

| Cache | Key | Kept across declarations | Validity |
|---|---|---|---|
| infer | frozen closed term | yes | the stamp rule below |
| whnf | frozen closed term | yes | the stamp rule below |
| defeq successes | pair of frozen closed terms (ordered) | yes | the stamp rule below |
| defeq failures | pair | no; cleared per declaration | used only by engine R (05.5) |
| unfold | (constant, level list) | yes | a constant never changes once added |
| level normalize | level handle | yes | levels do not depend on the environment |

- **Closed terms only.** Session entries have keys without free variables. Entries with free variables live in the scratch tier and die with it.
- **Stamp rule.** Each entry records the highest constant index used in its derivation. A worker uses an entry only if that index is below the current job's cut (08.3.2). An implementation may record a larger number, for example the length of the environment when the entry was made, and use the entry only if that number is not above the cut. This rule uses fewer entries. Lemma 10.4.4 proves that both rules are safe.
- **Size.** Each session is bounded, by default 128 MiB per worker. Eviction is by a CLOCK policy over entries. Eviction is always safe.
- **Order of jobs.** The scheduler gives a worker consecutive jobs from the same module where possible, so that session entries are reused. This is the "namespace grouping" of gruszka.

## 08.5 Caches inside a declaration

- Each cache is an epoch-cleared open-addressing table (04.8). It is keyed on handles, and it compares the full key after a hash match. It never trusts a hash alone (04.2.3, #14576).
- Defeq caches store successes only, keyed on ordered pairs, as in the official kernel after #14806. There is no union-find.
- The infer cache has two tables, for check mode and infer-only mode, as in the official kernel (A§1.5). An infer-only result is never used to answer a check-mode query.

## 08.6 Engine R cost

Engine R (05.5) runs on F's "not equal" answers and on the confirm set (05.1).

- The bench harness counts R calls and R instructions separately.
- The budget is 0.08 T on Mathlib (08.1). If a corpus needs more, the fix is to improve F (so that F finds the equality itself), not to raise the budget.
- On rejected declarations R runs in full. A reject is rare in real corpora, and the Arena bad tests are small.

## 08.7 Measurement

### 08.7.1 Method

- The P1 numbers are measured exactly as the Arena measures them: `perf stat -e instructions:u` over all threads, on the lean4export NDJSON input, parse included (02.2). Virtual time is instructions divided by 6.0 G per second.
- The official baseline is `leanchecker --from-export` of the same release, run on the same machine in the same week.
- Results are published as a JSON file per run, in the Arena results format, so they can be compared directly.

### 08.7.2 Harness

`rulean-bench` runs:

| Suite | Corpus | When | Gate |
|---|---|---|---|
| quick | Init, Std, the Arena `perf/` tests | every pull request | instructions on Init and Std within +1% of `main`; no `perf/` test above 1 virtual second (P1.d) |
| full | Mathlib, CSLib, Cedar, Navier-Stokes | each night | P1.a and P1.b ratios; memory at most 4 GiB (P1.f); wall at most 60 s on 8 threads (P1.e) |
| scale | FLT (Anthropic), RH project | each week | ratio at least 10 (P1.c); memory and wall time recorded |

Instruction counts are deterministic to within about 0.1% for a single-threaded run. The pull-request gate uses a single-threaded run for that reason.

GitHub-hosted runners do not expose the hardware counters, so `perf` cannot count instructions on them. `rulean-bench` has three counters for that reason: `perf` (the Arena measure), the `I refs` of valgrind cachegrind (no hardware counter, about 50 times slower), and `instructions retired` of `/usr/bin/time -l` on macOS (includes the system calls). The P1 numbers and the baseline use `perf`. The other counters are for a trend on one machine and must not be compared with Arena numbers.

### 08.7.3 Profiling

- Each engine phase has a counter (number of calls, nodes made, cache hits and misses). Counters are compiled in and cost one increment each.
- `rulean check --profile` writes the counters and the 100 most expensive declarations.
- Instruction-level profiling uses `perf record` on Linux and Instruments on macOS. The build keeps frame pointers (`-C force-frame-pointers=yes`). They cost about 1% and make every profile usable.

## 08.8 Performance rules for contributors

1. No allocation in a hot loop. Use the arenas.
2. No `HashMap` from `std` in the core. Use `rulean_store::Table` (10.6).
3. No recursion on term depth. Use explicit stacks (05.11).
4. Every new cache states its key, its validity rule and its twin lemma before it is merged.
5. A pull request that changes engine F includes the quick-suite numbers in its description.
