# 08. Performance

This document turns promise P1 (02.2) into budgets, names the techniques that pay for them, and specifies how performance is measured and protected in CI.

Evidence: research/B-kernels-and-performance.md sections 8 to 10, and research/A section 5.

## 08.1 The budget

The P1.a target is at most 1.21 T instructions on the Arena Mathlib export, including parsing. Mathlib has about 700 k declarations.

| Phase | Budget, instructions | Per declaration | Official today | Best known (unverified) |
|---|---|---|---|---|
| read and parse (07) | 0.16 T (NDJSON) or 0.03 T (`.rlb`) | 230 or 45 | 1.66 T (14%) | nano-lean whole pipeline about 68 per byte |
| scheduling, environment cuts, merge | 0.02 T | 30 | none | |
| engine F: infer, whnf, conversion | 0.85 T | 1.2 M | about 10 T | nano-lean about 0.5 M, gruszka about 0.53 M |
| engine R rescues and confirmations (05.1) | 0.08 T | 0.1 M | | |
| inductives, recursor generation, quotients | 0.05 T | | | |
| report, axiom closure | 0.02 T | | | |
| **total** | **at most 1.18 T** (margin 0.03 T) | **at most 1.7 M** | 12.10 T (v4.35.0) | 0.40 T |

The stretch goal is 0.60 T. That is 20 times fewer than v4.35.0 and 16 times fewer than the 2026-11-14 nightly. It is the planned answer to the official kernel getting faster (15.2).

Every budget row has a counter in the bench harness (08.7). A pull request that makes a row exceed its budget on the Init or Std corpus fails CI.

## 08.2 Where the factor comes from

The factors are ranked by evidence (B§10.2). They multiply only roughly, so the plan has margin.

| Rank | Technique | Expected factor vs official | Evidence | Spec |
|---|---|---|---|---|
| 1 | NbE with glued values and lazy delta by value | 3 to 6 | the top three Arena kernels all use NbE, 0.40 to 0.53 T, against 2.6 to 5.8 T for substitution kernels in Rust; 100 to 1000 times on the `perf/` tests | 05.4 |
| 2 | handle store, struct of arrays, no reference counting | about 2.3 | con-ron against con-leche, same algorithm, 3.85 T against 8.85 T; allocation and RC are 25% of the official profile | 04 |
| 3 | fast input | about 1.15 (removes most of the 14%) | official parse-only 1.66 T; MM0; gruszka Susz | 07 |
| 4 | session caches across declarations | 1.2 to 2 (to be measured) | gruszka sessions, measured only in its design doc | 08.4 |
| 5 | build tuning: fat LTO, one codegen unit, PGO | 1.1 to 1.2 | con-ron −11.6% on Init with LTO | 13.3 |
| n/a | threads | none on instructions | 3 to 9 times wall time at 4 to 8 threads, +3.5% instructions | 08.3 |

con-ron is at 3.47 T. Techniques 1, 3 and 4 must give a further factor of 2.9 over con-ron to reach 1.21 T (B§10.1). Technique 1 alone gives about 5 to 14 times among unverified Rust kernels. So the plan needs about half of what NbE gave those kernels.

## 08.3 Parallel scheduling

Parallelism does not help P1 (instructions). It is needed for P1.e (60 s wall on 8 threads).

### 08.3.1 Dependency graph

- After parsing, the scheduler computes the direct constant references of each declaration (type and value). This is one pass over the frozen store with a per-node "constants below" summary, cached per node.
- A declaration can be checked when all its references have been **added** to the environment. Added means the constant is known with its type, not that its check has finished. This is how the official kernel works in parallel elaboration: later declarations use the type of a theorem before its proof is checked.
- So the scheduler has two stages per declaration: **add** (register the constant, cheap, in declaration order) and **check** (the expensive part, in parallel). Inductive declarations are added only after they are checked, because their recursors are generated by the check.
- A later declaration may be checked before an earlier one it uses has finished its check. If the earlier check fails, the run verdict is `reject`, and the report marks the later declarations as `depends-on-rejected`. Theorem T1 applies only to a run whose verdict is `accept`, so this order is sound.

### 08.3.2 Environment cut

- Each check job sees the environment of all constants added before it, in input order. That is the environment that the official kernel would see when replaying the export in order.
- The environment is an append-only array of constants indexed by declaration number. A cut is a number: "constants with index below k". So a cut costs nothing to make or share.
- A worker that looks up a constant with index at or above its cut gets "unknown constant", exactly as the sequential replay would.

### 08.3.3 Jobs and granularity

- Mathlib parallelises almost completely: the slowest single declaration takes about 0.7 s (con-leche) and the slowest FLT declaration about 3.7 s (gruszka) (B§8.4).
- Jobs are groups of consecutive declarations from the same module, up to about 2 M instructions of estimated work, so the per-job overhead stays below 1%.
- Declarations with a large estimated cost are scheduled first (longest-processing-time first within the ready set). The estimate is the size of the value in nodes.
- con-leche reaches 8.8 times at 8 jobs, gruszka 5.2 times (B§8.4). The rulean target is at least 6 times at 8 threads on Mathlib.

### 08.3.4 Determinism

The verdict and the report do not depend on the thread count (T5, 10.1). The exceptions are the work counts `steps` and `interns` of the summary and the session and engine counts, because each worker does its own work in its own store. They depend on the thread count, but not on timing. Workers do not share caches. A session cache entry that one worker makes is not visible to another worker, so a worker's results depend only on its own job sequence. Each job's sequence is a function of the scheduler's deterministic job list, not of timing.

**Why not share caches between workers.** Sharing would save some work. It would also make the cache contents depend on timing. A cache entry is a true judgment, so sharing would still be sound, but it would make performance timing-dependent and the proof harder. rulean 1.0 does not share. A later release may add a read-only cache layer that is built in a first pass and then frozen.

### 08.3.5 Status in rulean 0.0.5

- The add stage runs on all declarations before the check stage starts. It adds each axiom, definition, theorem and opaque constant with a check of the name only, and it checks each inductive and quotient declaration fully. So the scheduler does not compute the dependency graph of 08.3.1, and each check runs after all declarations are added.
- An inductive check in the add stage can use a definition whose check has not run yet. If that definition is wrong, the verdict is `reject`, as 08.3.1 says. The report does not mark the later declarations as `depends-on-rejected` yet. It gives the first rejected declaration in input order, as a sequential run does.
- The check stage has 256 jobs of consecutive declarations with about the same cost, and not jobs of about 2 M instructions. The cost of a declaration is the number of distinct nodes of its type and its value. The workers take the jobs from a shared counter, the job with the largest cost first.
- A worker keeps its session from one job to the next (08.4). A new session for each job made the check stage about two times slower on the Init export. The job sequence of a worker depends on timing. The verdict, the rejected declaration, the quarantine and the axioms do not depend on it, because each session entry is a true judgment and the stamp rule applies at the cut of each job. The session counts and the engine F counts depend on it. A check that stops at a resource limit can also depend on it.
- Each worker has its own copy of the store and the environment, and not a shared `&Store` (03.5, K3). The memory grows by the size of the store for each worker. On Std, one thread uses 880 MB and four threads use 3285 MB.
- `--threads` has the default 1, which is the sequential check, and not the number of cores, because of the memory of the copies.

## 08.4 Sessions: caches across declarations

The official kernel clears its caches after each declaration. rulean keeps some of them in a per-worker **session** (B§8.3, gruszka).

| Cache | Key | Kept across declarations | Validity |
|---|---|---|---|
| infer | frozen closed term | yes | the stamp rule below |
| whnf | frozen closed term | yes | the stamp rule below |
| defeq successes | pair of frozen closed terms (ordered) | yes | the stamp rule below |
| defeq failures | pair | no; cleared per declaration | used only by engine R (05.5) |
| unfold | (constant, level list) | yes | a constant never changes once added |
| level normalize | level handle | yes | levels do not depend on the environment |

- **Closed terms only.** Session entries have keys without free variables. Entries with free variables live in the scratch tier and die with it.
- **Stamp rule.** Each entry records the highest constant index used in its derivation. A worker uses an entry only if that index is below the current job's cut (08.3.2). An implementation may record a larger number, for example the length of the environment when the entry was made, and use the entry only if that number is not above the cut. This rule uses fewer entries. Lemma 10.4.4 proves that both rules are safe.
- **Size.** Each session is bounded, by default 128 MiB per worker. Eviction is by a CLOCK policy over entries. Eviction is always safe.
- **Order of jobs.** The scheduler gives a worker consecutive jobs from the same module where possible, so that session entries are reused. This is the "namespace grouping" of gruszka.

## 08.5 Caches inside a declaration

- Each cache is an epoch-cleared open-addressing table (04.8). It is keyed on handles, and it compares the full key after a hash match. It never trusts a hash alone (04.2.3, #14576).
- Defeq caches store successes only, keyed on ordered pairs, as in the official kernel after #14806. There is no union-find.
- The infer cache has two tables, for check mode and infer-only mode, as in the official kernel (A§1.5). An infer-only result is never used to answer a check-mode query.

## 08.6 Engine R cost

Engine R (05.5) runs on F's "not equal" answers and on the confirm set (05.1).

- The bench harness counts R calls and R instructions separately.
- The budget is 0.08 T on Mathlib (08.1). If a corpus needs more, the fix is to improve F (so that F finds the equality itself), not to raise the budget.
- On rejected declarations R runs in full. A reject is rare in real corpora, and the Arena bad tests are small.

## 08.7 Measurement

### 08.7.1 Method

- The P1 numbers are measured exactly as the Arena measures them: `perf stat -e instructions:u` over all threads, on the lean4export NDJSON input, parse included (02.2). Virtual time is instructions divided by 6.0 G per second.
- The official baseline is `leanchecker --from-export` of the same release, run on the same machine in the same week.
- Results are published as a JSON file per run, in the Arena results format, so they can be compared directly.

### 08.7.2 Harness

`rulean-bench` runs:

| Suite | Corpus | When | Gate |
|---|---|---|---|
| quick | Init, Std, the Arena `perf/` tests | every pull request | instructions on Init and Std within +1% of `main`; no `perf/` test above 1 virtual second (P1.d) |
| full | Mathlib, CSLib, Cedar | each week, in the workflow `corpus` | P1.a and P1.c ratios; memory at most 4 GiB (P1.f); P1.b and P1.e are not measured in CI |
| scale | FLT (Anthropic), RH project | each week | ratio at least 10 (P1.c); memory and wall time recorded |

Instruction counts are deterministic to within about 0.1% for a single-threaded run. The pull-request gate uses a single-threaded run for that reason.

GitHub-hosted runners do not expose the hardware counters, so `perf` cannot count instructions on them. `rulean-bench` has three counters for that reason: `perf` (the Arena measure), the `I refs` of valgrind cachegrind (no hardware counter, about 50 times slower), and `instructions retired` of `/usr/bin/time -l` on macOS (includes the system calls). The P1 numbers and the baseline use `perf`. The other counters are for a trend on one machine and must not be compared with Arena numbers.

State of the harness:

- `rulean-bench gate` checks limits on each result of a run: the verdict, the instructions in virtual seconds, the peak memory and the wall time. It exits with code 1 if a limit fails.
- The workflow `nightly` runs rulean on the 225 Arena tests each night with the cachegrind counter. It then checks two gates: each verdict is correct with at most 4 GiB of peak memory, and no `perf/` test is above 1 virtual second (P1.d).
- The Init and Std gate of the quick suite uses the work count of 08.7.4 and not the instructions.
- The full suite is in the weekly workflow `corpus` (11.2), because that workflow already makes the exports of Mathlib, CSLib and Cedar, and one run of Mathlib takes more than one hour. After `rulean check`, the job runs `leanchecker --from-export` of the same release on the same export, and `scripts/corpus-gate.sh` checks three gates: both checkers accept the export, the CPU time of the official kernel is at least 10 times the CPU time of rulean (P1.a on Mathlib, P1.c on CSLib and Cedar), and the peak memory of rulean is at most 4 GiB (P1.f). The CPU time is the user time and the system time of all threads. The runner has no hardware counters, so this ratio takes the place of the ratio of instructions, and it is not the Arena measure. P1.b needs the official nightly, and P1.e needs 8 threads on a workstation, so the job records the wall time but does not check them. Navier-Stokes uses Lean 4.34.0-rc2 and is out of scope (02.5).
- The scale suite is not written yet. It cannot run on a GitHub-hosted runner. The export of FLT (Anthropic) is 37.8 GB, and the runner has about 14 GB of free disk, 16 GB of memory and a limit of 6 hours for each job. The RH project has about 17.5 M lines and about 1.06 M declarations, so its export and its oleans are also too large for the runner. The suite needs a self-hosted machine with at least 128 GB of memory and 200 GB of disk, or a larger hosted runner. Until that machine is available, the M4 item "FLT (Anthropic) and RH checked" stays open. Both projects also use Lean v4.33.1, which is out of scope (02.5). At commit 6e837e75 of 2026-09-24, the file `lean-toolchain` of `anthropics/fermats-last-theorem` names `leanprover/lean4:v4.33.1`. Question Q7 of 15.4 records this conflict.
- In November 2026, on an Apple M-series machine, rulean gives the correct verdict on all 225 tests, but 16 of the 42 `perf/` tests take more than 2 s of wall time. The largest is `perf/magma-list-deep-n36`, with 243.7 G instructions (about 40 virtual seconds) and 3.2 GB of peak memory. So P1.d is not met.

### 08.7.3 Profiling

- Each engine phase has a counter (number of calls, nodes made, cache hits and misses). Counters are compiled in and cost one increment each.
- `rulean check --profile` writes the counters and the 100 most expensive declarations.
- Instruction-level profiling uses `perf record` on Linux and Instruments on macOS. The build keeps frame pointers (`-C force-frame-pointers=yes`). They cost about 1% and make every profile usable.

State of the profiling:

- The option `--profile` of `rulean check` selects the semantics profile (05.2), so the counters need another option name. The counters are not written yet.
- The JSON report has the field `slowest`, with the 10 slowest declarations of a sequential run and the wall time of each (09.4).
- The manual workflow `profile` runs `scripts/profile.sh` on a GitHub-hosted runner. The script exports Init, `Init.Prelude` or Std of Lean v4.36.0 and runs `rulean check` with one thread under callgrind or cachegrind. The artifact has the instruction count of each function, with and without the functions that it calls. With the input `test`, for example `perf/magma-list-deep-n21`, the job checks the export of that Arena test and does not run leanexport, and the input `engine` selects engine R or engine F. A time sample on macOS gives more weight to the cache misses, so it does not show where the instructions are. The Arena counts instructions.
- Valgrind does not run the SHA instructions of the CPU, so under callgrind and cachegrind `rulean-io` uses the portable SHA-256 code (12.4). The Arena counts with `perf` on the CPU, which uses the SHA instructions if the CPU has them. On a large input, the counts of valgrind are therefore higher than the counts of the Arena. The first callgrind profile of Init (v4.36.0, 348 MB) has 275.8 G instructions. Of these, 47.7 G (17.3%) are in the portable `sha256::compress`, because the input is hashed during the parse and again by `confirm` after the run. The functions with the next largest costs, without the cost of the functions that they call, are `Nodes::get` (5.3%), `inst_rec` (5.0%), `Table::put` (4.0%), `intern_expr` (4.0%), the probe of the expression table (2.9%) and the cache of engine R, `Memo::find` and `Memo::put` (about 4.4% together). On the small `perf/` tests, the digest is a very small part of the count.
- On the slow `perf/` tests, one to three declarations take nearly all of the time. On `perf/app-lam`, the declaration `dag_app_binder` takes 6.0 s, and the trace has no conversion rule. So the time is in the type inference of engine R, which puts a new local into each lambda body by substitution, as the official kernel does. Engine F has type inference now (05.4.5). With `--engine F`, this test uses 0.55 G instructions and not 50 G. Engine R is still the default engine, so the default time does not change.
- On `perf/magma-list-deep-n21`, engine F does not help: it uses 17.2 G instructions, and engine R uses 16.4 G. The declaration `countermodel` closes its goal with `decide`, and engine F evaluates the full decision procedure in one query. Engine F keeps each value that it makes until the end of the declaration, so this query fills the arena (`MAX_NODES`, 2^18 nodes in one array). Then engine F stops with a fault, and engine R checks the query again. With 2^20 and 2^22 nodes, the query still fills the arena. On the 31 `perf/` tests that take less than 5 s, the total with engine F is 155.4 G instructions with 2^18 nodes, 167.3 G with 2^20 and 284.0 G with 2^22, and `perf/grind-ring-5` goes from 21.3 G to 37.5 G and 131.0 G. So a larger limit is not the fix. Engine F needs a way to free the values of a step that is done, and this is an open item of M4. The other 48 fallbacks of engine F on this test are "not equal" answers where engine R finds "equal". Each of them costs little.
- A count of the values in the full arena of this query shows two causes. First, `eval` has no cache, and each application of the closure of the `decide` proposition evaluates the list of 441 entries again, so the arena holds about 96 copies of the list. A cache of the values of closed terms for one declaration removes these copies. Second, each lookup `table[idx]!` walks the list by structural recursion, and each step makes values of `List.below`, `List.rec` and `PProd` that engine F keeps. With the cache and 2^22 nodes, the query still fills the arena, and the run uses 20.7 G instructions. Without the cache, the query fills the same arena. On the 31 short `perf/` tests the cache alone uses more instructions, for example 17.8 G against 17.3 G on this test and 23.9 G against 21.4 G on `perf/grind-ring-5`, so it is not in the code. Only a way to free the values of a finished step can let engine F finish this query.

### 08.7.4 Work gate

The quick suite gate of 08.7.2 must run on each pull request, on a GitHub-hosted runner. Such a runner has no hardware counters, and cachegrind is about 50 times slower than the checker. A check of Init takes about 296 G instructions, so cachegrind on Init and Std takes too long for a pull request. For this reason, the gate measures the work of the checker with counts in the code and not with instructions.

- **Work count.** The JSON report has two counts in `summary` (09.4). `steps` is the number of calls of `enter` of the type checker. Each level of infer, whnf, the definitional equality, the evaluation of engine F and the inference of engine F calls `enter` once. `interns` is the number of calls of `intern_expr` of the store, with the calls that find the node. It follows the substitution and the parse, which `steps` does not show. For example, `perf/app-lam` gives 57 355 steps and 40 029 106 interns. The work count is `steps` plus `interns`.
- **Determinism.** The core has no hash function with a random seed and no shared state, so a sequential run gives the same counts on each machine and on each run. The gate has no noise for this reason. With `--threads` above 1, the jobs of the workers start from different caches, so the counts can change from one run to the next. The gate uses `--threads 1`.
- **Baseline.** The file `docs/bench/work.json` has the work count and the Lean version of each export of the gate. The gate does not compare with a build of `main`. It compares with this file, which follows `main`, because each pull request that changes the work by more than the tolerance must change the file too.
- **Gate.** `scripts/work-gate.sh` exports Init and Std of the Lean release of CI with leanexport, checks each export with one thread, and runs `rulean-bench work`. The gate fails if a work count differs from the baseline by more than 1% in either direction, if the Lean version is not the version of the baseline, or if the verdict is not accept. A decrease fails too, because a baseline that stays above the real count hides a later regression of the same size. On a failure, the script prints the new baseline, so that a pull request that changes the work on purpose can put it in the file. With `WRITE=1`, the script writes the file.
- **Limits.** The work count is not the time. A change can make each step slower and keep the count. The nightly bench with the instruction counter (08.7.2) finds such a change. The CI job `lake comparator` runs the gate. This job depends on the Lean release, so it is not a required check.

## 08.8 Performance rules for contributors

1. No allocation in a hot loop. Use the arenas.
2. No `HashMap` from `std` in the core. Use `rulean_store::Table` (10.6).
3. No recursion on term depth. Use explicit stacks (05.11).
4. Every new cache states its key, its validity rule and its twin lemma before it is merged.
5. A pull request that changes engine F includes the quick-suite numbers in its description.
